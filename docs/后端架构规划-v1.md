# AI 装机助手 · 后端架构规划 v1

> 本文是后端的整体规划（不是实施代码）。目标读者是负责实现的工程师 / Codex。
> 规划原则：贴合现有 SwiftUI 前端已经存在的数据结构与功能，不引入前端不需要的东西。
> 前端代码为唯一现状真相来源（`May/May/Models/` 与 `May/May/Screens/`）。

---

## 0. 最重要的一条原则（决定整个架构）

CLAUDE.md 明确要求：

> **AI 不能自由发明硬件型号；具体推荐必须来自一个维护中的推荐/硬件数据库。**

因此后端**不是**"把用户输入丢给大模型让它直接吐配置"。后端的核心是三个**确定性数据服务**：

1. **硬件库（Hardware Catalog）** —— 型号、规格、接口、兼容关系的唯一真相源。
2. **价格库（Price Service）** —— 来自现有 `tools/hardware-price-crawler` 的人工复核参考价。
3. **兼容性 / 规则引擎（Rules Engine）** —— 插槽匹配、电源余量、高U低显等可判定规则。

大模型（LLM）只承担三类**受约束**的工作：
- 把用户的模糊意图 / 粘贴的报价文本，解析成**结构化约束**；
- 在后端**给定的候选型号列表里**做排序和挑选（用 function calling / 枚举 ID，永远不让它自由输出型号名）；
- 生成给小白看的**自然语言解释**（理由、风险话术、升级建议措辞）。

最终产物必须**再经规则引擎校验**（预算、兼容性、电源），不通过就重选。这样既有 AI 的体验，又杜绝幻觉型号。

## 2. 技术栈建议

> 这些是**推荐默认值**，第 11 节列出需要你拍板的关键决策。

| 层 | 选型建议 | 理由 |
| --- | --- | --- |
| 部署区域 | **国内云**（阿里云 / 腾讯云）+ **ICP 备案** | 面向中国小白用户，延迟与合规（App 上架、内容审核）都要求国内 |
| 后端框架 | **Python + FastAPI** | AI/LLM 编排为核心；现有爬虫已是 Python，硬件/价格数据管线可复用同一生态。备选：Node/TypeScript（NestJS）若团队更熟 TS |
| 主数据库 | **PostgreSQL** | 硬件库/价格/配置/社区都强关系型；JSONB 存灵活规格字段 |
| 缓存 / 会话 / Feed | **Redis** | 验证码、token、社区 Feed 缓存、热度计数 |
| 对象存储 | **阿里云 OSS**（或腾讯云 COS） | 社区图片、App 素材 |
| LLM | **Claude API**（`claude-opus-4-8` 主力 / `claude-haiku-4-5` 跑解析类轻任务） | 结构化输出 + function calling 成熟；国内访问需经服务端代理，客户端永不直连 |
| 鉴权 | 手机号验证码 + **Sign in with Apple**（App Store 要求）+ 可选微信 | 国内主流；Apple 登录是上架硬性要求 |
| API 风格 | REST + JSON（OpenAPI 描述）；客户端→服务端→LLM | 与 SwiftUI `Codable` 直接对接 |

**关键安全约束**：客户端绝不持有任何 LLM / 价格源密钥；所有 AI 调用经后端编排。

## 4. 数据模型（核心表）

> 字段命名尽量对齐前端 `Codable` 结构，减少映射成本。下面是关键表，非完整 DDL。

### 4.1 硬件库（Hardware Catalog）—— 基石

直接以现有 `HardwareCatalog.swift` 为种子数据导入。当前 Swift 里每个 `HardwareCatalogItem` 是 `{id, name, brand, detail}`，但 `detail` 是混合字符串（如 `"14代 Raptor Lake Refresh · LGA1700"`）。后端要**把 detail 拆成结构化字段**，让规则引擎能用。

```text
hardware_component
  id            text  PK          -- 复用 Swift 里的 id，如 "i5-14600k"
  category      text              -- cpu | gpu | motherboard | ram | storage | psu | cooler | case
  name          text              -- "i5-14600K"
  brand         text              -- Intel / AMD / NVIDIA ...
  detail_raw    text              -- 保留原始字符串，便于回溯
  specs         jsonb             -- 结构化规格（见下）
  is_recommended bool             -- 是否进入推荐池（对应"维护中的推荐库"）
  status        text              -- active | eol（已停产）
  updated_at    timestamptz

-- specs 按 category 不同：
-- cpu:   { socket: "LGA1700", platform: "Raptor Lake Refresh", gen: 14,
--          cores, threads, tdp, perf_index }     ← perf_index 供性能/升级用
-- gpu:   { series: "RTX 40", vram_gb, tdp, perf_index }
-- motherboard: { socket, chipset, platform, form_factor, mem_type: "DDR5" }
-- ram:   { type: "DDR5", capacity_gb, speed }
-- storage: { type: "PCIe 4.0", capacity_gb }
-- psu:   { watt, rating: "80+ Gold", modular }
```

> 兼容性逻辑（socket 匹配）现在写在 `HardwareCatalog.areCompatible(cpu:motherboard:)`。
> **后端 = 唯一真相源**，从 specs 派生；前端那份兼容判断可保留做离线兜底。

### 4.2 价格库（来自爬虫）

## 5. AI 功能的编排设计（最关键部分）

每个 AI 功能都遵循同一骨架：**结构化输入 → 规则/数据取候选 → LLM 受约束挑选与措辞 → 规则复校 → 返回**。

### 5.1 AI 一键装机 `POST /v1/build/generate`

**输入**（对应 `AIBuildView` 的 state）：
```jsonc
{
  "budget": 6850,
  "useCase": "游戏",                 // 游戏 | 办公 | 游戏兼办公
  "gameCategories": ["FPS"],
  "officeApps": [],
  "purchasePreference": "全新优先",
  "chassisColor": "曜石黑",
  "cpuPreference": "任意",           // 或指定 specifiedCPU
  "gpuPreference": "任意"
}
```

**流程**：
1. **预算分配**：按 useCase 把总预算拆到各品类（游戏→显卡占比高；办公→CPU/内存均衡）。
   v1 用**人工维护的"档位模板"**（budget tier × useCase → 各品类目标价 + 推荐型号池），稳、可控、可解释。后续再演进成算法分配。
2. **候选检索**：每个品类在 HardwareDB（`is_recommended=true`）+ PriceDB 里取**符合子预算且通过兼容性**的候选列表。
3. **LLM 挑选**：把候选（带 id/规格/价格）喂给 Claude，用 **function calling 让它只能从候选 id 中选**，并产出每个部件的 `reason` 和 `alternative`（也必须是候选 id）。**禁止自由文本型号**。
4. **规则复校**：总价 ≤ 预算、CPU↔主板插槽一致、电源瓦数 ≥ 估算功耗、无高U低显失衡。失败则反馈给 LLM 重选（限重试次数）。
5. **组装** `BuildPlan`：parts(含 `source="参考价"`) + risks（由规则引擎生成，映射到 `pass/warning/error`）。

**输出**：直接对齐 `BuildPlan` / `PCPart` / `BuildRisk`，前端零改动即可渲染。

### 5.2 配置排雷 `POST /v1/review/analyze`

**输入**：用户粘贴的自由文本（如 `"i7-14700F + RTX4060 + H610 主板 + 500W 电源，商家报价 6999"`）。

**流程**：
1. **LLM 解析**（haiku 级即可）：自由文本 → 结构化部件 + 商家报价。
2. **型号归一**：模糊匹配到 HardwareDB 的 component_id（匹配不上的标记为未知，照样能给部分结论）。
3. **规则引擎判定**：高U低显、主板档次配不上 CPU、电源余量不足、插槽不匹配、**报价 vs 参考价是否虚高**。
4. **LLM 措辞**：生成 `conclusion`（能不能买）+ 每条 `risk` 的解释 + **可直接发给商家的回复话术**。

**输出**：对齐 `ConfigReviewResultView` 的 `conclusion + [BuildRisk] + 话术`。

### 5.3 升级建议 `POST /v1/upgrade/plan`

**输入**：`HardwareProfile`（当前电脑）+ 预算。

**流程**：
1. 用 specs 的 `perf_index` 找**瓶颈件**（CPU/GPU 失衡、内存不足、机械盘等）。
2. 受兼容性约束生成**升级顺序**（如换 CPU 是否被迫换主板/平台）。
3. 在预算内按"每元性能提升"排序，LLM 生成通俗的升级理由与措辞。

### 5.4 游戏性能测试 `POST /v1/perf/estimate`

**输入**：`HardwareProfile` + `resolution`(1080p/2k/4k) + `games[]`。

**流程**：
- 优先查 `benchmark` 实测点；缺失时用**派生模型**估算：
  `est_fps ≈ f(gpu.perf_index, cpu.perf_index, game_weight, resolution_factor)`，用已有实测点标定。
- 瓶颈 = 比较 CPU/GPU 的 perf_index 与该分辨率的偏向。
- 输出对齐 `PerformanceTestResult`（averageFPS / lowFPS / bottleneck / advice）。

> 注意：现在前端 `PerformanceTestFlow` 的 FPS 是硬编码的（142/118/72）。后端要给出**有数据支撑的估算**，并对置信度做提示（小白也要知道这是估算）。

### 5.5 兼容性检查 `POST /v1/compat/check`
纯规则引擎，无需 LLM：插槽、内存代际(DDR4/DDR5)、电源瓦数、机箱尺寸。复用 5.1 的规则模块。

## 6. 规则 / 兼容性引擎（确定性，无 AI）

集中实现，被装机/排雷/升级/兼容性复用。至少覆盖：

- **插槽匹配**：CPU.socket == Motherboard.socket（已有 Swift 逻辑可移植）。
- **内存代际**：Motherboard.mem_type == RAM.type。
- **电源余量**：Σ(部件 tdp) × 安全系数 ≤ PSU.watt。
- **失衡检测**：高U低显 / 低U高显（用 perf_index 比值阈值）。
- **档次匹配**：主板供电/芯片组 vs CPU 等级。
- **价格合理性**：实付 vs 参考价区间。

每条规则产出 `{level: pass|warning|error, title, detail}`，直接映射前端 `RiskLevel`。

## 7. 硬件 + 价格数据管线（接入现有爬虫）

现有 `tools/hardware-price-crawler` 产出 `approved-reference-prices.csv`（人工复核后）。后端新增：

1. **种子导入**：一次性脚本把 `HardwareCatalog.swift` 解析进 `hardware_component`（拆 detail → specs）。这是硬件库初始化。
2. **价格摄取**：提供受保护的 `POST /admin/prices/ingest`（或离线脚本），把 `approved-reference-prices.csv` 灌进 `component_price`。**保持"人工确认后才发布"的现有纪律**，不自动抓取上线。
3. **推荐池维护**：后台标记 `is_recommended` / `status=eol`，控制 AI 能选哪些型号 —— 这就是 CLAUDE.md 说的"维护中的推荐库"。

## 9. 横切关注点

- **合规**：ICP 备案；社区 UGC 必须接**内容审核**（图片+文本），先审后发或先发后审按规模定；用户实名（手机号）。
- **限流与成本**：AI 接口按账户限流；解析类任务用便宜模型（haiku），方案生成用 opus；缓存相同输入结果。
- **可解释性**：AI 输出始终带"为什么"（产品原则），并标注价格为"参考价"+ 更新时间。
- **降级**：LLM 不可用时，装机退回纯模板方案，排雷退回纯规则结论 —— 保证核心功能不挂。
- **观测**：记录每次 AI 调用的输入/候选/最终选择，便于追查幻觉与调优。

## 10. 实施路线（建议给 Codex 的阶段顺序）

> 依赖关系：核心数据服务是一切的地基，必须最先做。

- **Phase 0 — 地基**
  1. 工程脚手架（FastAPI + Postgres + Redis + 部署）。
  2. 硬件库种子导入（`HardwareCatalog.swift` → DB，拆 specs）。
  3. 价格摄取脚本（对接爬虫 CSV）。
  4. 规则/兼容性引擎（移植并扩展 Swift 兼容逻辑）。
  5. 账户/登录 + Profile 同步（取代本地存储）。

- **Phase 1 — 决策类 AI（产品核心价值）**
  6. AI 一键装机（先模板分配 + 受约束 LLM 挑选）。
  7. 配置排雷（解析 + 规则 + 话术）。
  8. 配置中心 CRUD（保存方案 / 当前电脑）。

- **Phase 2 — 进阶 AI**
  9. 升级建议。
  10. 性能测试（基准表 + 派生模型）。
  11. 兼容性检查接口收口。

- **Phase 3 — 社区**
  12. Feed / 发帖 / 评论 / 点赞收藏 / 图片 / 审核。

- **Phase 4 — 打磨**
  13. 装机指南内容服务、流式响应、降级、成本与限流优化。

## 11. 需要你拍板的关键决策

1. **部署区域 / 合规**：确认面向国内用户、走国内云 + ICP 备案？（影响选型与上线周期）
2. **后端语言**：默认推荐 Python/FastAPI（贴合 AI + 复用爬虫生态）；若你或 Codex 更想要 TypeScript/NestJS 也可，需尽早定。
3. **AI 装机首版策略**：先"人工档位模板 + LLM 挑选"（稳、可解释，推荐），还是直接上"算法预算分配"？
4. **社区优先级**：社区是否进 MVP？它工作量最大（审核/Feed/社交图），可放到决策类功能跑通之后。
5. **性能测试数据**：是否接受 v1 用"少量实测点 + 派生模型估算"并明确标注为估算？还是必须真实基准数据库（成本高很多）？
