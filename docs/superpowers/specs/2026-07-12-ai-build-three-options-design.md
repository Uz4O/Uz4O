# AI 装机三方案接入设计

## 目标

将 AI 装机流程接入真实后端。用户提交需求后，结果页同时提供二手、全新、混合采购三套基底方案；首屏只展示核心组合，点击后查看完整八大件。

第一阶段只根据预算和游戏方向匹配基底配置。内存容量、存储容量、Wi-Fi/蓝牙、无显卡方案、后期升级和颜值需求保留在前端流程中，但不参与本阶段的配置调整。

## 覆盖范围

- 预算范围：3000～20000 元。
- 档位间隔：500 元。
- 共 35 个价位档。
- 每档包含 FPS、3A、均衡三个方向。
- 每个方向包含全新、二手、混合三种采购模式。
- 最终应有 315 套结构化基底配置。
- 每套配置总价不得超过目标预算 200 元。
- 每套配置包含 CPU、主板、显卡、内存、SSD、电源、散热器和机箱八大件。

### 判定规则

- 所选游戏全部属于重 CPU 时，方向为 `fps`。
- 所选游戏全部属于重 GPU 时，方向为 `aaa`。
- 所选游戏全部属于均衡类时，方向为 `balanced`。
- 所选游戏跨越两个或三个类别时，方向为 `balanced`。
- 选择“什么都玩”时，方向为 `balanced`。
- 游戏分类由后端统一执行，避免不同客户端产生不同结果。

## 采购模式

- 全新：八大件全部使用全新参考价和可购买的全新型号。
- 二手：八大件全部按照二手采购规则和二手参考价生成。
- 混合：主板、显卡、SSD 和电源使用全新配件；CPU、内存、散热器和机箱可使用二手配件。
- 停产且没有全新参考价的型号不得进入全新位置。
- 二手和混合方案必须在详情中展示对应的成色、保修和硬件风险。

## 后端接口

保留现有 `POST /v1/build/generate`，新增批量推荐接口：

```text
POST /v1/build/options
```

请求沿用现有装机请求字段，至少包含预算、用途和所选游戏。后端先计算游戏方向，再以相同预算和方向分别匹配 `used`、`new`、`mixed` 三种方案。

响应必须一次完整返回三套方案。每套方案包含：

- 采购模式
- 模板 ID
- 标题
- CPU 和 GPU 名称
- 参考总价
- 八大件及其成色、参考价格和价格日期
- 优点、缺点、风险和适用用户
- 兼容性结果

任一采购模式不存在时，接口返回明确错误，不以其他采购模式冒充，也不返回残缺的成功结果。

## 低价位数据

现有 3000、3500、4000、4500、5000、6500 和 7000 元文档作为人工配置参考。新增 5500 和 6000 元档，并补齐所有低价位档缺失的方向和采购模式。

低价位数据转换为与 7500～20000 元模板相同的结构，统一进入硬件目录、参考价格和模板导入流程。生成和导入时执行以下检查：

- 35 个价位档完整。
- 每档恰好包含 9 个方向与采购模式组合。
- 八大件齐全且角色不重复。
- 配件成色符合采购模式。
- CPU 与主板兼容。
- 电源功率满足整机需求并保留合理余量。
- 分项价格之和等于参考总价。
- 总价不超过目标预算 200 元。

## iOS 数据流

`AIBuildView` 在最后一步构造请求并调用三方案接口。请求期间禁用重复提交并显示生成中状态。

成功后进入方案选择页，按二手、全新、混合展示三张摘要卡。每张卡只显示：

- 采购方式
- `CPU + GPU` 核心组合
- 参考总价
- FPS、3A 或均衡方向

用户点击卡片后进入现有配置详情页面，查看八大件、价格、优缺点和风险。结果不再使用 `AppMockData.samplePlan`。

请求失败时留在当前流程，保留用户选择并提供重试。后端返回数据不完整或无法解码时按失败处理，不展示模拟配置兜底。

## 第一阶段边界

以下选项会保留在请求模型中，但第一阶段不调整基底配置：

- 内存容量
- SSD 容量
- Wi-Fi/蓝牙
- 无显卡方案
- 后期升级计划
- 机箱颜色和颜值风格

下一阶段再基于这些硬需求对三套基底进行降档、替换或加价判断，并继续遵守最高超预算 200 元的规则。

## 验证标准

- 后端测试覆盖游戏分类、跨类归为均衡、三采购模式完整返回和缺失数据失败。
- 数据测试确认 315 套模板、35 个档位和每档 9 套组合。
- 公网 `POST /v1/build/options` 能返回三套完整配置。
- iOS Debug 和 Release 环境使用各自既有 API 地址。
- iOS 模拟器构建成功。
- 模拟器中完成生成、摘要选择、详情查看、失败重试流程。
- 3000、7000、7500、20000 元边界档位分别进行一次端到端验证。
